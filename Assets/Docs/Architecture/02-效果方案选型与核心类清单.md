# 效果系统方案选型（对应需求「三.4」）

这是整个架构最关键的一次选择。六个候选方案逐个评估：

## 方案对比

### 方案 A：每种效果一个独立 class
> Monster Train 的做法：`CardEffectDamage` / `CardEffectDraw` / `CardEffectHeal` … 共 74 个，加上 `CardTrait*` 43、`RelicEffect*` 162、`StatusEffect*State` 54，合计 **333 个效果类**。

- ✅ 每个类职责单一、易读、可独立测试。
- ✅ 新效果不影响旧效果。
- ❌ 类数量爆炸。Monster Train 有专职团队；个人开发到 150 个类时会开始记不住哪个类做什么。
- ❌ 大量重复：`CardEffectDamage` / `CardEffectDamageByUnitsKilled` / `CardEffectDamagePerTargetAttac` 三个类只是伤害数值算法不同。
- **判定：思路对，粒度错。**

### 方案 B：枚举 + 参数（`switch(effectType)`）
```csharp
enum EffectType { Damage, Block, Draw, ... }
switch (e.type) { case EffectType.Damage: ... }
```
- ✅ 类极少，一眼看完。
- ✅ 序列化最简单，纯值类型，存档友好。
- ❌ 一个巨型 switch，加到 40 个分支后无法维护。
- ❌ 参数字段必须是所有效果的并集（`paramInt1..paramInt6`），Inspector 里全是无关字段——Monster Train 的 `CardEffectData` 已经踩了这个坑（20+ 个 `paramXxx` 字段）。
- ❌ 无法做「效果组合子」（重复/条件/随机）。
- **判定：小项目可用，但本项目要求支持组合效果，不合适。**

### 方案 C：ScriptableObject 效果对象
> 每个效果实例是一个 `.asset` 文件，卡牌引用它们。

- ✅ 可视化编辑，可复用（多张卡引用同一个「造成 6 点伤害」）。
- ❌ **资产文件爆炸**：200 张卡 × 平均 2.5 个效果 ≈ 500 个 .asset 文件，还要命名管理。
- ❌ 复用是陷阱：改了共享的效果资产会同时改掉十几张卡。
- ❌ **最致命**：SO 是共享实例，如果效果里不小心写了字段（比如缓存 target），就变成跨战斗的全局状态污染。这正是需求里「不要让 SO 保存运行时状态」要防的事。
- **判定：否决。**

### 方案 D：Command 模式
> `ICommand { Execute(); Undo(); }`，出牌产生命令入队。

- ✅ 天然支持撤销、回放、网络同步。
- ❌ `Undo()` 在卡牌游戏里极难正确实现（伤害、抽牌、洗牌都要逆运算）。
- ❌ 除非要做 PVP 或「时间倒流」机制，否则纯粹增加复杂度。
- **判定：为模式而模式，否决。**（若将来要做重放，用「记录随机种子 + 玩家输入序列」重演，成本远低于 Undo。）

### 方案 E：数据驱动效果列表（外部 JSON/CSV/表格）
- ✅ 策划可改，无需重编译，热更新友好。
- ❌ 无编译期检查，改错一个字段名要运行到才发现。
- ❌ 需要额外写导表工具、编辑器、校验器——这本身是个子项目。
- ❌ Unity Inspector 已经是个免费的表格编辑器。
- **判定：内容量到 500+ 张卡再考虑；现在否决。**

### 方案 F：少量通用 Effect 类 + 参数配置
> 比如只有 `DamageEffect`，通过 `EffectValue` 支持「固定 6 点」「每层力量 2 点」「等于当前护甲」。

- ✅ 类数量最少。
- ✅ 参数只出现在需要它的类上，Inspector 干净。
- ❌ 单纯的 F 无法表达「重复 3 次」「若敌人有中毒则…」这种结构。

## 最终选择：**F + A 的混合 —— `[SerializeReference]` 多态效果类 + 组合子**

具体形态：

```csharp
[Serializable] public abstract class CardEffect {
    public TargetSelector Target;
    public abstract void Apply(EffectContext ctx);
    public virtual bool CanApply(EffectContext ctx) => true;
    public virtual string Describe(DescribeContext d) => "";
}
```

`CardDefinition`（SO）里：
```csharp
[SerializeReference] public List<CardEffect> Effects = new();
```

**`[SerializeReference]` 是这个方案成立的技术前提**（Unity 2019.3+）：它让抽象类的子类实例可以**内嵌**序列化进 SO，不需要单独的 .asset 文件，Inspector 里用下拉框选类型。这同时解决了方案 C 的资产爆炸和共享污染，以及方案 B 的字段并集问题。

**类的数量控制**：只写 14 个效果类（见目录 `Effects/Impl/`），其中 4 个是**组合子**：

| 类别 | 类 | 覆盖的需求 |
|---|---|---|
| 原子效果（10） | `DamageEffect` | 造成伤害、多段攻击（`Times`）、多目标、动态数值 |
| | `BlockEffect` | 获得护甲 |
| | `DrawEffect` | 抽牌 |
| | `EnergyEffect` | 获得/消耗能量（负数即消耗） |
| | `ApplyStatusEffect` | 加 Buff / Debuff（同一个类，正负由状态定义决定） |
| | `HealEffect` | 治疗（负数即扣血不过护甲） |
| | `DiscardEffect` | 丢弃（可指定随机/选择/全部） |
| | `ExhaustEffect` | 消耗手牌 |
| | `AddCardEffect` | 生成卡牌到手牌/牌堆/弃牌堆 |
| | `ModifyCardCostEffect` | 修改卡牌费用（本回合/永久） |
| 组合子（4） | `RepeatEffect` | 重复执行、连续效果 |
| | `ConditionalEffect` | 条件判断、条件效果 |
| | `RandomPickEffect` | 随机效果 |
| | `DelayedEffect` | 延迟执行 |

**「动态计算数值」不新增类**，交给 `EffectValue`：

```csharp
[Serializable] public struct EffectValue {
    public int Base;
    public ValueScale Scale;      // None / PerStatusStack / PerCardInHand / PerEnergy / PerBlock / PerCardTypePlayedThisTurn / PerEnemyAlive
    public string ScaleId;        // 比如 status id
    public int PerUnit;           // 每一单位加多少
    public int Multiplier;        // 整体倍率（默认 1）
    public int Evaluate(EffectContext ctx, BattleUnit target);
}
```

「造成 X 点伤害，X 等于你的护甲」= `DamageEffect { Amount = { Base=0, Scale=PerBlock, PerUnit=1 } }`，零代码。

**判定依据总结**：
1. 类数量：14 个核心效果类 vs Monster Train 的 333 个。
2. 编译期安全：`[SerializeReference]` 直接存类型，重命名有 `[MovedFrom]` 兜底，比 `Type.GetType(字符串)` 安全。
3. 无资产爆炸、无共享状态污染。
4. 支持组合结构（重复/条件/随机/延迟），这是纯枚举方案做不到的。
5. 90% 的卡零代码。

**代价（诚实说明）**：
- `[SerializeReference]` 序列化的数据在**类改名后会丢失引用**，必须配 `[UnityEngine.Scripting.APIUpdating.MovedFrom]` 或不改名。
- Unity 默认的 `[SerializeReference]` Inspector 体验一般，建议第 2 阶段写一个 60 行的 `PropertyDrawer` 提供「+ 添加效果」下拉菜单。
- 效果类必须**严格无状态**（不能有可变字段），因为一个 `CardDefinition` 的效果实例被该卡所有 `CardInstance` 共享。这条要写进 code review checklist。
